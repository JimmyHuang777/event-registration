**怎麼加**：新決議加在對應分類的最上面，編號格式 `D-YYYYMMDD-nn`（當天第 nn 筆）。決議被推翻時不要刪舊的，在舊的標「已被 D-xxx 取代」並新增一筆。

## 原則

### D-早期-01　手機與 Dashboard 兩邊都要有　`#原則` `#對照`
- **決定**：每個功能 LIFF（手機）與 Dashboard 都要做，交付時說明對照；只在 Dashboard 的例外限於：管理者角色與權限、Word／Excel 匯入、CSV／PDF／Excel 匯出、報名者管理、火車時刻、仙佛紀念日管理。
- **原因**：管理者需要在手機現場處理，也需要在電腦批次處理；兩邊不一致會讓人找不到功能。
- **否決**：只做其中一邊再補。
- **影響**：所有功能；見 FEATURES.md 對照欄。

### D-早期-02　新增或改名 Edge Function 要同步改 workflow　`#部署` `#原則`
- **決定**：更新 `.github/workflows/deploy-edge-function.yml` 的 `paths` 與 Deploy step，並單獨交付該檔。
- **原因**：沒進 workflow 的函式不會自動部署，且部署一律要 `--no-verify-jwt`，否則會被 Supabase 閘道 401 擋住。
- **否決**：手動在 Supabase 後台部署。
- **影響**：`.github/workflows/deploy-edge-function.yml`、DEPLOY.md。

### D-早期-03　「先討論／先確認再行動」＝只討論，不動手改　`#原則` `#溝通`
- **決定**：使用者這樣說時只提出看法與選項，等使用者決定後才改程式。
- **影響**：工作流程。

### D-早期-04　推送前先跑 `git diff`　`#原則` `#部署`
- **決定**：每次交付都提醒，確認只有預期的檔案有變動。
- **原因**：避免舊檔覆蓋新檔（曾發生 GitHub 與本機版本不同步）。
